# Структура содержательного кейса

`lib/case-studies.ts` хранит данные презентации, `components/case-study.tsx` — универсальную серверную страницу. В `lib/content.ts` остаются общие данные карточек проектов и метаданные маршрутов. Страница `/cases/[slug]` выбирает расширенную презентацию по slug; отсутствие данных сохраняет прежний вариант страницы. Sunny Rentals получил отдельный содержательный кейс исходной системы собственного проката. Sunny Booking — отдельный мультипарковый этап; материалы new в этот кейс не включены. Food Market не добавлен в публичный список без фактов и изображений.

## Следующий проект

1. Добавить подтверждённые базовые данные проекта в `cases` в `lib/content.ts`.
2. Добавить запись `CaseStudy` в `caseStudies`, используя тот же slug. Количество модулей произвольное; идентификаторы уникальны в проекте.
3. Для каждого модуля задать задачу, возможности и реальные проверенные изображения с исходными размерами, alt и подписью. `label` задаёт короткое название переключателя нескольких изображений.
4. Заполнить подтверждённые технологии, инженерные особенности, качественные результаты и контактный блок. Заголовки и пояснения разделов находятся в данных.
5. При необходимости передать отдельную интерактивную демонстрацию через `demonstration`. Универсальные компоненты не знают тематику или slug проекта. Текущая `CaseGallery` подключается маршрутом и не менялась.

`CaseModules` — переключаемые модули с клавиатурной навигацией; все тексты присутствуют в серверном HTML. Без JavaScript модули открыты последовательно, доступны ссылки на изображения. `CaseImageViewer` — общий просмотрщик с нативным dialog, Escape, восстановлением фокуса, режимом оригинального размера и прокруткой широких изображений на мобильном.

## Редакторская история проекта

Обложка может задавать собственные `title` и `subtitle`, не меняя общие карточки и маршрутизацию. Необязательные `story` (заголовок и абзацы) и `photography` (заголовок, абзацы, реальные изображения) добавляют компактное вступление перед демонстрацией. `CaseModule.detail` позволяет разделить объяснение на два коротких абзаца. У проектов без этих полей прежний вывод сохраняется.

Для «Дымоход-Трейд» сведения о старом сайте, полном цикле разработки, фотосъёмке, обработке и наполнении предоставлены владельцем в редакторском ТЗ. Функции, стек и связи данных сверены с реализацией по таблице выше. Исторические оценки удобства старого сайта — рассказ владельца, не результат UX-исследования. Измерения экономического эффекта, рост продаж, автоматическая публикация SEO-статей и искусственное сравнение «до / после» не добавлены. Генерация SEO-материалов описана как подготовка текста из характеристик с отдельным черновиком/публикацией, без обещаний результатов продвижения.

Уточнение владельца: «Дымоход-Трейд» — производство дымоходов и комплектующих, не поставщик. На обложке используется формулировка «для производителя». Прежний кадр трубы из семейства признан владельцем генеративным и заменён фотографией конкретного SKU; источник указан в CASE_SCREENSHOTS.md.

`capabilities` — массив объектов `{ label, icon? }`. Поддерживаемые нейтральные ключи Lucide: `code`, `files`, `sliders`, `dashboard`; подпись обязательна, иконка декоративная. Четыре иконки импортированы явно в презентацию; управление мокапами не меняется.

## Автоматизация смет и КП

Акцент обновлён в обложке, модуле «Клиенты и сметы» и существующем разделе результатов. Необязательные `outcomeComparison` (подписанные последовательности шагов) и `outcomesNote` добавляют компактное сравнение и качественную обратную связь только там, где они заданы в данных. Историю ручной подготовки смет и положительную оценку заказчика предоставил владелец в ТЗ; численные показатели не добавлены.

В текущем коде `ManagerEstimateCard.tsx` подтверждены поиск и добавление позиций из каталога, замена SKU, количества, сохранение редакций и PDF; CSS содержит мобильные варианты. Отдельного интерфейса создания пустой сметы в админке не найдено: не заявляем самостоятельное создание с нуля как реализованную кнопку. Прямое обращение описано через исходный подбор менеджером в существующем конфигураторе и дальнейшую правку сохранённой сметы. Используется прежний безопасный `estimate-editor-desktop.webp`; новые кадры добавления изделий или мобильной сметы не выдумываются, снимки с персональными данными не публикуются.

## Мобильные изображения модулей

`CaseImage.mobile` — необязательный вариант изображения со своими `src`, размерами, alt и подписью. Превью использует `<picture>` с границей 767 px; увеличенный просмотр, ссылка на файл и подпись выбирают тот же вариант через `matchMedia`/`useSyncExternalStore`, включая изменение ширины окна. Без JS браузер также выбирает мобильный источник в `<picture>`. Если пары нет, десктопный кадр и увеличение сохраняются. Мокапы не меняются.

Пары: карточка трубы → мобильная карточка дефлектора; маршрут в конфигураторе → мобильный первый шаг; SVG → мобильная схема; каталог → мобильная категория; фотографии семейства → имеющийся мобильный редактор фотографий/FAQ. Различия состояния пояснены в подписях. PDF и FAQ уже представлены мобильными снимками. Для редактора состава и SEO-полей позднее добавлены два безопасных кадра, отдельно переданных владельцем (источники в CASE_SCREENSHOTS.md). Теперь все десктопные снимки модулей имеют мобильную пару; PDF и FAQ остаются мобильными на всех экранах. Снимки клиентов не публикуются.

Порядок внутри функционального модуля: скриншот с увеличением → заголовок и пояснение → возможности. Навигация модулей сохраняется сверху на телефоне и слева на компьютере. В интерактивной демонстрации порядок переключателей «Телефон / Ноутбук», телефон выбран по умолчанию; выбранный экран сохраняется при смене устройства.

## Sunny Rentals и общая 3D-демонстрация

Данные Sunny — `lib/sunny-case.ts`, размеры публичных снимков — `lib/sunny-assets.ts`. `CaseGallery` принимает `CaseDemo` (`lib/case-demo.ts`); прежний кейс использует `chimneyDemo` по умолчанию. Экраны каждого устройства фильтруются по наличию реального снимка, без нерелевантных замен. При переключении сохраняется тема, доступная на обоих устройствах; иначе выбирается первый доступный экран. Route key сбрасывает состояние при смене кейса. Размеры и alt увеличенного снимка берутся из данных. Геометрия и жесты моделей сохранены. `CaseStudy.nextProject` — необязательный редакционный блок перед сотрудничеством, `href` задаётся только для существующего кейса.

Проверенные источники и обработка приватных полей перечислены в `docs/SUNNY_RENTALS_CASE.md`. Более ранняя пометка «Sunny в разработке» относилась к прежнему обобщённому представлению. В новом ТЗ владелец прямо подтвердил использование исходного Sunny Rentals в собственном прокате; статус этого кейса — «Собственный проект». Это не заявление о внедрении Sunny Booking у сторонних прокатов.

## Sunny Booking

Отдельные данные — `lib/booking-case.ts`, изображения — `lib/booking-assets.ts` и `public/cases/sunny-booking/`. Источники, проверенный стек, ограничения и обезличивание описаны в `docs/SUNNY_BOOKING_CASE.md`. Только снимки `new`, без экранов CRM/AI старого Sunny Rentals. Используются прежние `CaseStudyPage`, `CaseModules`, `CaseImageViewer` и `CaseGallery`; геометрия и управление моделей не меняются. Необязательные `siteLabel` и `nextProject.linkLabel` позволяют назвать внешний пример витрины и ссылку на предшествующий проект; значения по умолчанию сохраняют предыдущие кейсы. Карточка, генерация маршрута и sitemap получают третий проект из общего списка `cases`.
